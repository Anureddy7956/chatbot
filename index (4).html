From Chatbot to Agent

Build an autonomous agent step by step — each step adds one new memory type

Step 1 — No Memory → Step 2 — Short-Term → Step 3 — Long-Term → Step 4 — Semantic → Step 5 — Episodic → Step 6 — Full Agent

What We're Building

A chatbot just responds to whatever you say. An AI Agent perceives the situation, plans what to do, and acts — then repeats. The key ingredient that separates them is memory.

In this module, we start from a chatbot with zero memory and progressively add all four types. By the end, you'll have an agent that remembers who you are across sessions, searches a knowledge base, and keeps a diary.

The 4 Memory Types

1. Short-Term Memory

The current conversation — kept as a list in RAM. Gone when the program closes.

conversation_history = []

2. Long-Term Memory

Facts saved to a JSON file on disk. Survives restarts. Stores name and preferences.

user_profile.json

3. Semantic Memory

A knowledge base in FAISS. The agent searches it before answering to find relevant facts. Index is built once and saved to disk.

knowledge.index + knowledge_docs.json

4. Episodic Memory

A diary of past interactions — what was asked and what was answered, timestamped.

agent_diary.json

STEP 4

Semantic Memory (FAISS)

File: step_04_semantic.py

Long-term memory stores facts about users. Semantic memory stores knowledge about the world. We use FAISS — a local vector database that finds the most similar text to a given query. The index is built once on first run using Gemini embeddings and saved to disk — no re-seeding on future runs. Before answering, the agent searches for relevant background knowledge and injects it into context.

Architecture — Step 4

flowchart TD U([User Query]) --> RK[retrieve_knowledge\nFAISS similarity search] RK --> |found| INJ[Inject into context\nas background knowledge] RK --> |not found| SKIP[Skip injection] INJ --> G[Gemini call\nwith enriched context] SKIP --> G G --> R([Response]) style RK fill:#7c3aed,color:#fff style INJ fill:#ede9fe

[No domain knowledge injected.
 Relies only on model's training.]
Key concept: FAISS uses embeddings — each text is converted to a list of numbers (via Gemini's gemini-embedding-001 model) that captures its meaning. Similar texts have similar numbers. When you query, FAISS finds the texts whose numbers are closest to your query's numbers. No exact keyword matching needed. The index is saved locally as knowledge_s4.index so embeddings are only computed once.

STEP 5

Episodic Memory (Agent Diary)

File: step_05_episodic.py

Episodic memory is a timestamped diary of past interactions. Every query and response is saved to agent_diary.json. The agent (or you) can review past conversations across sessions.

STEP 6

Full Agent — Perceive → Plan → Act

File: solution.py

The final step wires all 4 memory types into a proper agent loop. We add Perception (classify the user's intent) and Planning (decide which action to take) before Acting. This is the foundation of every AI agent architecture.

Architecture — Step 6 (Final)

flowchart TD U([User Input]) --> PER[Perceive\nclassify intent via Gemini] PER --> PL{Plan\nwhich action?} PL --> |update_name| UN[Update profile\nsave_profile] PL --> |use_tool| UT[Call search_topic tool\nquery FAISS] PL --> |respond| RS[Generate response\nfull context] UN & UT & RS --> ACT[Act: return response] ACT --> STM[(Short-term\nhistory list)] ACT --> EPI[(Episodic\nagent_diary.json)] ACT --> U LTM[(Long-term\nuser_profile.json)] --> PER SEM[(Semantic\nFAISS)] --> RS style PER fill:#6366f1,color:#fff style PL fill:#6366f1,color:#fff style ACT fill:#059669,color:#fff

💡 Perceive function

# perceive() asks Gemini to classify
# the user's intent as JSON:
{
  "intent": "inform_name",
  "topic": null,
  "name_mentioned": "Alex"
}

# plan() maps intent to action:
"inform_name" → "update_name"
"tool_needed"  → "use_tool"
otherwise      → "respond"
